# Vetic Calling Agent — from a Twilio MVP to a rebuilt agent with its own dashboard

*An AI PM case study, written from the builder's seat.*

## Executive summary

Vetic runs pet grooming appointments; when one goes badly, a human agent calls the owner to apologize, log the complaint, and promise a fix. This project automated that call: a Twilio + Claude MVP, rebuilt on LiveKit + OpenAI after the MVP hit a real, measured latency ceiling, backed by an eval harness (a 30-case golden set, 30/30 pass) and, later, a purpose-built observability dashboard the agent reports into. The standout decision was rejecting a cheaper-looking model swap — `gpt-5.4-nano` had a lower headline input price than `gpt-4o-mini`, but a real, timed 100-query run showed it was slower and, on output tokens, actually more expensive; the incumbent stayed. The most interesting finding, though, wasn't a metric — it was what a "100% passing" eval report actually turns out to mean once you open it up. A later 100-query routing sweep caught 39 real classification failures; roughly two-thirds were genuinely fixed and re-verified against the judge, but the script that assembled the final "reconciled" report hardcoded a pass verdict into every row rather than reading back real results — a meaningful share of the "fixed" cases were never actually re-confirmed. That's not a footnote; it's the same lesson as the sentiment/completion-rate gap below, told twice.

Fixing that reconciliation gap for real — not just naming it — became its own investigation. Git history confirmed the production agent hadn't been touched since before the legacy grading that produced the "39 failures," so the claimed fix couldn't have come from a prompt change; reading the actual reconciliation script confirmed it re-graded the *same* previously-captured transcripts against a corrected expected-answer key, never a fresh agent response. A real live rerun against the current, unmodified agent found the true number was 20 of 39, not the roughly-two-thirds the reconciled report implied. Two rounds of real prompt fixes followed — verify, edit, re-verify, never assert — landing on an honest 71/100 (outbound) and 72/100 (inbound) classification pass rate, now synced live to the dashboard in place of the earlier fabricated 100/100. A newly-added empathy rubric, closing the "sentiment scoring: absent" gap below, surfaced a sharper and still-unresolved finding: 95% empathy pass on outbound calls, roughly 4% on inbound, unmoved by two independent, verified fix attempts. The honest number stayed the deliverable, not a forced 100%.

## The problem

Following up with an unhappy customer is high-value, repetitive work: apologize where warranted, log the complaint, promise a resolution — and a bad follow-up call turns one bad appointment into a lost customer. The brief wasn't "build a chatbot that talks." It was whether an AI agent could run the structured, empathetic part of that call reliably, at phone-call latency, without inventing promises the business can't keep. This was a solo build (one author, git history from 2026-06-23 through at least 2026-08-30) under an explicit $0-hosting constraint — a hosting branch for Fly.io was built and then shelved the same day once it became clear Fly.io has no free tier for an always-on worker. The first build, a Twilio + Claude MVP, worked, but its own latency notes named the problem before the fix existed: on real test calls, caller-perceived latency ran to roughly 5.3 seconds per turn, and the project's own `latency_optimization.md` says outright that "perceived lag is what makes the agent feel robotic" — with a from-scratch move to a real-time, WebRTC-style architecture already ranked as the last, biggest lever on the list, before anyone built it.

## Defining success — how I measured a good call

This is the section I'd lead with in an interview, because it's honest rather than tidy: what got measured and what actually mattered turned out to be two different things.

**What's real:** an LLM-judged rubric (12+ tagged business rules — no unauthorized refunds, no missed ETA, no repetition, correct emergency routing, and several security/jailbreak checks) graded a 30-case golden set at 30/30. A separate identity-resolution stress test hit 90/100 first-try matches, using real database lookups rather than keyword guessing. A later, larger routing-classification sweep (100 simulated calls) caught 39 real misroutes; the "fully reconciled" report that followed claimed about two-thirds fixed but was assembled with hardcoded, unverified pass marks for a meaningful share of the rest. That gap has since been closed for real: a live rerun against the unmodified production agent found the true number was 20/39, not two-thirds — see below.

**What's confirmed absent from both codebases, not just unmentioned:** a completion-rate metric, and any check that a promise actually gets kept. Stage 3 of the script promises a callback "within 2–3 hours"; no code path anywhere schedules it. A call can pass every rubric check while the promise it made goes unkept. Compliance and outcome are still being conflated for promise-keeping, and only the first is instrumented. Sentiment used to sit in this same absent category — nothing computed it, the only related code was a comment explaining why Twilio's profanity filter is *disabled*, so the model can read real emotional language rather than "****" — until a real EMPATHY_ACKNOWLEDGMENT rubric tag was added and live-tested: it grades whether the agent gives a genuine, feeling-specific acknowledgment, not a bare apology, before moving to resolution. What it found was a real, uncomfortable result, not a clean addition — see below.

## The eval harness and dashboard

The harness (`rubric.py` + `run_eval.py`) grades simulated transcripts against tagged rules using `gpt-5` as an independent judge model, deliberately separate from the `gpt-4o-mini` agent under test. Worth naming honestly: both are OpenAI models, so a same-family self-grading bias risk remains — accepted, not solved.

The concrete story of the harness earning its keep: a 100-query routing-classification sweep found 39 real failures — 17 fell back to a generic, unnamed escalation; 12 named the wrong team; 10 resolved the issue without escalating at all. The report that followed claimed roughly two-thirds genuinely fixed and re-verified live, with the fix said to have grown new deterministic misroute-correction logic in the production agent. Building the final "100% passing" report exposed a second, more interesting bug: the compile script hardcoded a pass verdict into every row instead of reading back a real result, and at least 23 of the 100 rows carry a pass with either a documented real fail as their last actual grade, or no supporting re-grade at all. The expected "correct" team for several cases was also redefined mid-investigation, which mechanically inflates a pass rate independent of whether the agent improved. State it plainly: an eval pipeline that can silently report "fully passing" without re-checking every case is a real product risk, not a cosmetic one — arguably a sharper finding than the routing bugs it was built to catch. (Following that story further, below, turned up that even the "new deterministic misroute-correction logic" claim didn't hold up — the agent code was never actually touched.)

The dashboard side came later, and from a different codebase — internally called the Vetic dashboard, and rebranded "Meridian" only in its user interface (the builder's own progress log never uses that name, describing it instead as "the persistence + dashboard layer [that] has always been missing"; full writeup in [that repo's own README](https://github.com/tanishqd1216-source/ai-call-agent-master#readme)). It's a real product: a Postgres-backed Next.js app with a call-history view, a per-turn latency timeline, an ERP-style department/agent picker, and CRM/MCP integration management, reached in development through a fixed, reserved ngrok domain. It originally had an `/evals` section consuming this same harness's results too — that's since been decommissioned in favor of LangSmith, see below. Checking it live turned up 117 real call records already logged — more than the project's own notes describe — but also a real inconsistency worth naming: its public-facing marketing pages show hardcoded claims like "92%+ First-Contact Resolution" that aren't computed from anything in that same database.

Fixing the reconciliation problem for real turned out to be its own case study in measurement discipline. Cross-referencing git history showed `agent_outbound.py`/`agent_inbound.py` hadn't been committed to since before the legacy grading that produced the "39 failures" — so the claimed fix couldn't have come from a prompt change. Reading the actual reconciliation script confirmed it: it re-graded the *same* previously-captured transcripts against a corrected expected-answer key, not a fresh agent response. A real live rerun of those 39 cases against the current, unmodified agent — plus the 49 cases that had never been independently tested at all — found the honest classification pass rate was closer to 70% than 100%, in both directions.

Two rounds of real prompt/logic fixes followed the same discipline: make a change, then actually re-run the judge against a live call, never assert. Round one landed several genuine fixes but also introduced four new outbound and five new inbound regressions — direct, uncomfortable proof that this prompt's instructions aren't modular; editing one category's wording measurably shifted behavior on unrelated categories. Round two recovered some of those and fixed two more real coverage gaps, but also surfaced something more interesting than any single bug: the same case, unedited between runs, flipped from passing to failing between verification passes — real LLM sampling noise, not a regression, and a reminder that a single eval pass is not proof, even of a negative result. Final state, synced live to the dashboard in place of the earlier fabricated 100/100: 71/100 outbound, 72/100 inbound on classification.

The empathy rubric told a sharper story once it existed and got run for real: 95% pass on outbound calls, roughly 4% on inbound, across two independent, evidence-based fix attempts — the second confirmed, via direct transcript inspection, that the specific mechanism it targeted really was removed from the prompt, and the number still didn't move. That makes it a compliance-type gap, not a wording gap — the same category as two smaller classification misses found earlier, where the correct instruction already exists and the model simply doesn't reliably follow it. The decision was to stop iterating and report the real ~4% figure rather than either forcing a third fix attempt or quietly dropping the metric because it was inconvenient.

The dashboard's `/evals` section — Postgres tables and all — has since been decommissioned entirely, and the eval harness moved onto LangSmith as the actual system of record: two reference datasets, six real historical milestones backfilled with an honest accounting of what timing/token data is genuinely real versus synthetic, and `run_langsmith_eval.py` as the go-forward runner. Dropping the three Postgres tables (16 runs, 331 results) was done with a full backup taken first and verified against the live database afterward — the same "check, don't assert" discipline as everything above, applied to decommissioning the eval-integrity story's own supporting infrastructure. See the [dashboard repo's README](https://github.com/tanishqd1216-source/ai-call-agent-master#readme) for what that repo still does now that `/evals` is gone.

## Key tradeoffs

**Model cost vs. latency.** `gpt-5.4-nano` listed a lower input price than `gpt-4o-mini`, but a real, timed 100-query run told a different story: 5.46M prompt tokens at a 96.7% cache-hit rate in about 14 minutes on `gpt-4o-mini`, versus a `gpt-5.4-nano` run killed partway through for running far longer with visibly worse per-call latency — and a higher effective output price. Kept the incumbent.

**Hosting: build vs. shelve.** A working Fly.io deployment branch was built, then abandoned the same day once its lack of a free always-on tier collided with a hard $0-hosting constraint — a real cost decision made against real infrastructure, not a hypothetical one.

**Architecture: ship simple, rebuild on evidence.** The Twilio webhook loop was the right MVP — it shipped fast and proved the conversation design on real calls — but it's a request/response loop dressed as a phone call. The rewrite to LiveKit's real-time architecture only happened once the MVP's own latency data justified it.

**Scope cut: compliance over outcome.** No system was ever built to verify that a promised callback actually happens. The harness grades promise-*keeping language*, not promise-keeping fact — a deliberate, if consequential, scope boundary.

**Chase 100% vs. ship the honest number.** After two real, verified fix rounds on the inbound empathy gap — each confirmed to have made its intended prompt change, neither moving the pass rate off roughly 4% — the call was to stop rather than keep spending real API budget on a third attempt with no new hypothesis, and to report the true figure rather than removing the metric that produced it.

## Evolution: MVP → rebuild → dashboard

The Twilio MVP surfaced its own successor before anyone built it: the same latency document that diagnosed "perceived lag" as the core UX problem also scoped the eventual rewrite, in writing, as "the big win, the big rework." The LiveKit rebuild that followed immediately surfaced new problems the MVP had never been tested against — an emergency-location fallback that never fired after six repeated questions, and a no-ETA rule that existed only in the inbound agent, not outbound — both found by a stress test, fixed the same day, and re-verified with real scripted calls. The dashboard layer came last, and wasn't planned upfront: it was built once the gap of having no persistence anywhere "has always been missing," in the builder's own words — observability as a belated but deliberate product decision, not a day-one one.

## Impact

Being honest about what this project can and can't claim: there's no adoption, cost-saved, or business-impact number anywhere in either codebase — this was never deployed at real call volume. What's real and quantified: a 96.7% prompt-cache hit rate measured on a real 100-query run; a genuine classification-routing regression caught, with the true fixed rate later confirmed by live rerun at 20 of 39 — not the roughly-two-thirds the original reconciled report implied (see above); two further rounds of real, re-verified prompt fixes that moved the honest classification pass rate to 71/100 (outbound) and 72/100 (inbound), now synced live to the dashboard; one real security leak found and fixed — a config endpoint that returned an entire `.env` file, secrets included, to any caller, patched with a server-side allowlist; and real calls placed and recorded on both builds, including two real Twilio call recordings with transcripts and a real LiveKit browser test call with measured sub-second time-to-first-audio-byte.

## What I'd change with more time

1. **Build real outcome verification** — not just rule-compliance, but confirmation that a promised callback actually happened.
2. **Resolve the judge's self-grading bias** with a genuinely different model family from the agent under test.
3. **Replace the identity-resolution keyword detector** — it produced its own false positives in testing; a deterministic database check shouldn't need a heuristic layer on top.
4. **Reconcile the dashboard's marketing claims with its own real, computed stats** before anything customer-facing ships.
5. ~~Fix the eval-reconciliation process itself~~ — **done**: git-verified the claimed fixes weren't real, live-reran the actual agent, and resynced the dashboard to the honest 71/100 / 72/100 result.
6. **Resolve the inbound empathy gap structurally, not with wording** — two independent, verified wording-level fixes didn't move a ~4% pass rate; this likely needs the acknowledgment gated as a hard, separate turn the model can't skip, not another instruction tweak.
7. **Re-verify with multiple trials per case, not one** — a single eval pass demonstrably flips some cases on sampling noise alone; a trustworthy pass-rate number needs repeated runs to separate real signal from noise.

## Reflection: the PM lens

The clearest product lesson here wasn't in the agent — it was in the measurement. Building an eval harness before proving demand was the right prioritization call under real ambiguity, and the cost/latency decision (rejecting a cheaper-looking model on real timed data instead of vendor headline pricing) is the kind of call that only looks obvious in hindsight. But the eval-integrity finding is the one I'd spend the most interview time on: the gap between "the report says 100%" and "100% of the report is actually true" is exactly the gap a PM is supposed to be paranoid about, in this project as much as in the product it was built to measure. The empathy rubric added afterward reproduced that same lesson a second time, independently: two real fix attempts, each verified to have changed the prompt exactly as intended, and the number still didn't move — which is itself the more honest, more interesting finding to lead with than a clean pass rate would have been.
